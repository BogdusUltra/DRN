# ADRN: Advanced Distributed Robotics Network
## Подробная Архитектура Системы (System Design Document)

Данный документ описывает полное устройство системы, чтобы избежать потери контекста при разработке. Система ADRN представляет собой гибридную P2P платформу для оркестрации робототехники и IoT-устройств.

---

### 1. Топология сети (Control Plane vs Data Plane)
Система жестко разделяет управление (Control Plane) и передачу тяжелых данных (Data Plane).

*   **Архитектор (Client UI):** Веб-приложение (ReactFlow). Работает в браузере. Отвечает только за отрисовку графов и панелей управления. Подключается к Оркестратору по REST/WebSockets.
*   **Оркестратор (Control Plane Server):** Единый центр управления (Python). Хранит проекты, ключи шифрования, логи. Раздает инструкции машинам. **Не пропускает через себя данные нод (видео и т.д.)**, чтобы не стать "бутылочным горлышком".
*   **Исполнители (Worker Nodes):** Физические устройства (Raspberry, ПК) с установленным Python-демоном (Маячком). 
    *   Связь с Оркестратором: Защищенный туннель (команды, логи, телеметрия).
    *   Связь друг с другом (Data Plane): Напрямую (P2P) через **ZeroMQ** для передачи данных.

---

### 2. Жизненный цикл и Развертывание (Discovery & Deployment)
1.  **Поиск в сети (Discovery):** Worker-демоны при запуске используют широковещательные UDP-пакеты (Broadcast/mDNS) для объявления о себе: "Я Машина X, мой IP, мой открытый ключ".
2.  **SSH Авто-деплой:** Если машина новая, Архитектор может по SSH (введя логин/пароль) закинуть на нее скрипт Worker-демона, добавить его в автозагрузку и сгенерировать RSA-ключи.
3.  **Безопасность (Security):** 
    *   Вся локальная база Оркестратора (конфиги, история, ключи) зашифрована **AES-256**. Для доступа к Оркестратору нужен мастер-пароль.
    *   Общение между Оркестратором и Workers идет по зашифрованному каналу.

---

### 3. Управление Запусками (Jobs, Sessions & Multi-tenancy)
*   **Build Mode (Проекты/Blueprints):** Режим создания логики. Граф связей, параметров и скриптов.
*   **Run Mode (Сессии/Sessions):** При нажатии "Запуск", проект отправляется в Оркестратор. Оркестратор создает изолированную **Сессию**. Build Mode остается доступным — можно редактировать проект дальше или запустить его вторую копию.
*   **Контроль ресурсов (Collisions):** Оркестратор отслеживает физические ресурсы. Если Сессия А использует Камеру 1, а пользователь пытается запустить Сессию Б, которая тоже требует Камеру 1, Оркестратор выдаст предупреждение о конфликте и предложит остановить старую сессию.

---

### 4. Внутреннее устройство Нод (Node Internals)
*   **Class-Based Architecture:** Код каждой ноды оборачивается в Python-класс. Это позволяет ноде хранить состояние (`state`) между вызовами и дает программисту свободу выбора: использовать бесконечный цикл `while True` (например, для чтения камеры) или Event-driven подход (вызов функции при получении данных).
*   **ZMQ Буферизация:** У связей (Edges) есть режим:
    *   `Stream` (PUB/SUB с лимитом буфера): старые сообщения (кадры) отбрасываются, если приемник не успевает.
    *   `Default` (REQ/REP или PUSH/PULL): гарантированная доставка для критических команд.
*   **Унификация Параметров и Пинов:** Любой параметр (например, "Уверенность нейросети") может быть переключен в UI в режим "Пин". Если он Пин — константа из UI отключается, и нода начинает принимать значения из сети от других нод в реальном времени.

---

### 5. UI-Ноды и Управление в Реальном Времени (Dashboards)
*   В системе есть специальные **UI-Ноды** (Ползунки, Селекторы), которые живут на Канвасе и остаются активными даже в `Run Mode`.
*   *Финт с Селектором:* Если параметр ноды имеет тип `select` (выпадающий список) и переведен в потоковый режим, создается пара топиков. Одна нода (Publisher) шлет список доступных вариантов, UI-Селектор перехватывает их, отображает пользователю, и после клика пользователя отправляет выбранный вариант дальше (Subscriber).

---

### 6. Энтерпрайз-Функции (Отказоустойчивость и Логи)
*   **Оффлайн-зависимости (Air-gapped PyPI):** Если код ноды требует `import cv2`, Worker скачивает библиотеку не из интернета, а через встроенный в Оркестратор прокси-сервер. Для секретных предприятий без доступа в сеть, админ может загрузить `.whl` пакеты напрямую в Оркестратор.
*   **Распределенные логи (stdout/stderr):** Любой `print()` или краш `Exception` внутри кода ноды на Распберри перехватывается на уровне демона и отправляется в Оркестратор. Пользователь видит все ошибки сети в единой консоли UI.
*   **Heartbeats & Телеметрия:** Каждые 1-2 секунды каждый Worker отправляет в Оркестратор зашифрованный пинг: статус, загрузка CPU, RAM и заряд батареи. Если пинга нет — Оркестратор помечает машину как OFFLINE и бьет тревогу.

### 7. Модель Дистрибуции (Distribution & Naming)
Система официально называется **DRN (Distributed Robotics Network)** и распространяется в виде трех компонентов:

1.  **DRN-Agent (Маячок/Агент):** 
    *   Устанавливается на физические роботы и камеры.
    *   Распространяется как Python-пакет. Установка: `pip install drn-agent` (или напрямую из Git-репозитория).
    *   Предоставляет глобальную CLI-команду `drn` (например, `drn init`, `drn start`).
2.  **DRN-Server (Оркестратор):** 
    *   Мощный сервер (Backend на Python). Выполняет роль Control Plane.
    *   Предназначен для Enterprise-развертывания на выделенных серверах. Имеет спартанский веб-интерфейс только для системных администраторов.
3.  **DRN-Studio (Клиент):** 
    *   Десктопное приложение (Electron + React) и/или красивый Веб-сайт.
    *   *Для профи:* Ввод IP-адреса для подключения к удаленному `DRN-Server`.
    *   *Для казуалов (Standalone mode):* В приложении есть кнопка "Запустить локально". При нажатии приложение автоматически скачивает, распаковывает и запускает `DRN-Server` как невидимый фоновый процесс на компьютере пользователя и подключается к нему.
