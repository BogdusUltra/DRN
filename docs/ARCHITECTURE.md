# ADRN: Архитектура Системы

## Общая концепция
Система представляет собой распределенную платформу (похожую на K8s для IoT/Robotics) с разделением на плоскость управления (Control Plane) и плоскость данных (Data Plane).

### 1. Control Plane (Управление)
Состоит из двух компонентов:

*   **Оркестратор (Сервер):**
    *   Ядро системы, написанное на Python.
    *   Может запускаться как локально на ноутбуке, так и на выделенном сервере предприятия.
    *   **Обязанности:** Управление пользователями, авторизация (RBAC), хранение топологии графов (проектов), хранение SSH-ключей, сканирование сети, автоматический деплой скриптов-исполнителей (Workers) на конечные машины, сбор телеметрии и логов.
    *   **Безопасность:** Локальная база данных (SQLite) и конфигурации шифруются алгоритмом AES-256. Доступ к интерфейсу и данным возможен только после ввода мастер-пароля.

*   **Архитектор (Клиент UI):**
    *   Веб-приложение (React, React Flow), которое работает в браузере.
    *   Пользователь подключается к IP-адресу Оркестратора.
    *   **Обязанности:** Визуальное построение логики (ноды и связи), назначение задач на конкретные машины, просмотр логов в реальном времени.

### 2. Data Plane (Исполнение и Данные)
*   **Worker Nodes (Исполнители):**
    *   Физические машины (Raspberry Pi, ПК), на которых Оркестратором установлен Python-скрипт (Daemon).
    *   **Обязанности:** Выполнение Python-кода нод (обработка изображений, управление GPIO и т.д.).
    *   **Связь (Децентрализация):** Во время работы ноды передают полезные данные (видеопотоки, тензоры, координаты) **напрямую друг другу** (Peer-to-Peer) по протоколу **ZeroMQ** или через UDP. Данные минуют Оркестратор для максимальной скорости и снижения нагрузки на сеть.
    *   **Discovery:** Для обнаружения в локальной сети используется UDP Broadcast (широковещательные пакеты).

## Жизненный цикл проекта
1.  Оркестратор сканирует сеть (UDP) и находит пустые Raspberry Pi.
2.  Пользователь через UI вводит пароли, Оркестратор ставит на них Worker-скрипты по SSH.
3.  Пользователь строит граф в UI, назначает узлы на машины.
4.  При нажатии "Запуск", Оркестратор компилирует граф в набор инструкций (JSON) и раздает каждой машине её роль.
5.  Машины устанавливают ZMQ-соединения между собой и начинают работу.

### 3. Механизмы реального времени (Runtime Features)
*   **Heartbeats & Telemetry:** Каждый Worker периодически (каждые 1-2 секунды) отправляет Оркестратору зашифрованный пакет телеметрии. Пакет содержит статус (Alive), загрузку CPU, RAM и уровень заряда батареи. Связь идет по защищенному каналу (Control Plane).
*   **Унификация Параметров и Пинов:** Любой параметр ноды (например, порог чувствительности) может быть превращен во входной пин по клику тумблера в UI. Если пин отключен — параметр является заглушкой-константой. Если включен — параметр может изменяться в реальном времени данными от других нод.
*   **UI-Ноды (Dashboard Nodes):** Для управления работающей сетью используются специальные интерактивные ноды (Селекторы, Слайдеры, Кнопки). Они остаются активными во время работы сети. Например, UI-Селектор может принимать на вход массив строк от нейросети (Publisher) и отдавать выбранный пользователем вариант дальше по сети (Subscriber).
*   **Распределенное логирование:** Весь `stdout` и `stderr` (принты и ошибки) внутри пользовательского кода на Workers перехватывается на уровне демона и отправляется в Оркестратор для отображения в единой консоли Архитектора.
