# Жизненный цикл Машины (Worker) и Протокол связи

## 1. Жизненный цикл (От чистой машины до узла сети)

Чтобы избавиться от необходимости устанавливать библиотеки вручную (`pip install psutil` и т.д.), код Worker'а компилируется в автономный исполняемый файл (с помощью PyInstaller). Таким образом, на машину загружается только один бинарный файл.

### Этапы инициализации:
1.  **Доставка:** Бинарный файл (и папка проекта) перекидывается на чистую машину (Raspberry/PC) один раз (по SSH, флешкой или скачиванием).
2.  **Инициализация (Сброс):** Выполняется команда настройки. 
    `drn init --name "Rpi_Yard" --password "secret"`
    *Что происходит под капотом:* Сбрасывается белый список (Whitelist), генерируется пара RSA-ключей (Public/Private), пароль хэшируется и сохраняется в защищенный локальный конфиг.
3.  **Автозагрузка:** Скрипт прописывает себя в системный `autorun` (например, `systemd` на Linux).
4.  **Перезагрузка:** Машина перезапускается. С этого момента классический SSH нам больше не нужен. Все команды идут через наш протокол.

## 2. Процесс Авторизации (Handshake) и Pull-модель

В системе применяется **Pull-модель** (модель опроса). Агенты (машины) не спамят сеть своим полным состоянием; они лишь заявляют о своем существовании коротким маячком, а всю телеметрию (Heartbeat) Оркестратор запрашивает самостоятельно.

1.  **Beacon (Маячок):** Каждые N секунд (задается ключом `--beacon-interval`) Агент отправляет UDP Broadcast пакет: 
    `{"action": "beacon", "name": "Rpi_Yard", "public_key": "<RSA_PUB_KEY>"}`.
2.  **Проверка статуса (Ping / Heartbeat):** Как только Оркестратор видит новый маячок в сети, он немедленно отправляет TCP-запрос `ping` по адресу маячка, чтобы узнать статус авторизации. 
    * Если Оркестратор уже есть в WhiteList Агента, Агент отвечает зашифрованной телеметрией (Heartbeat). Оркестратор помечает узел как `auth`.
    * Если Оркестратора нет в WhiteList, Агент отвечает `{ "error": "Unauthorized" }`. Оркестратор помечает узел как `unauth` и больше не пингует его, ориентируясь только на приходящие UDP-маячки (для отображения статуса "Online").
3.  **Авторизация (Handshake):** Для неавторизованного узла оператор Оркестратора может инициировать Handshake. Оркестратор отправляет JSON по TCP (порт 50001): 
    ```json
    {
      "action": "handshake",
      "orchestrator_pub_key": "<ORCH_PUB_KEY>",
      "auth_payload": "<Base64_зашифрованной_строки>"
    }
    ```
    Где `auth_payload` — это зашифрованная *Открытым ключом Агента* строка `{"p": "secret", "h": "<sha256_of_orch_pub_key>"}`.
4.  **Проверка Агентом:** Машина расшифровывает `auth_payload` своим Private Key. 
    *   Сверяет хэш пароля `p` со своим эталонным хэшем.
    *   Сверяет `h` с реальным SHA256 хэшем от полученного `orchestrator_pub_key`.
    Если проверки успешны, Агент заносит `<ORCH_PUB_KEY>` в `whitelist.json` и отвечает `{"status": "ok"}`. После этого Оркестратор начинает периодически отправлять `ping` (Heartbeat) для сбора данных и поддержания активного статуса.

## 3. Универсальный Протокол Сообщений (JSON)

После авторизации общение идет по TCP. Из-за лимитов RSA (2048 бит шифрует лишь 214 байт) **любой payload (команда и ответ) автоматически разбивается на чанки**. Оркестратор и Агент прозрачно шифруют чанки и склеивают их, что позволяет передавать любые объемы данных (например, длинный вывод терминала).

Внутри передается стандартизированный JSON:

### Типы действий (Actions)
1.  **`ping`**: Запрос телеметрии (Heartbeat). Используется Оркестратором для пуллинга состояния авторизованных машин.
2.  **`echo`**: Отправка произвольного текста. Агент отвечает этим же текстом. Используется для проверки связи и целостности шифрования.
3.  **`terminal_cmd`**: Выполнение команд ОС в консоли (заменяет SSH). Возвращает stdout/stderr.
4.  *(В планах)* **`deploy_nodes`**: Передача JSON-структуры узлов, которые машина должна выполнить в Data Plane.
5.  *(В планах)* **`start_network` / `stop_network`**: Команда на запуск или остановку алгоритмов узлов.

## 4. Фоновое выполнение (Daemonization)
Для профессиональной работы Агент отвязывается от терминала (TTY), чтобы оператор мог закрыть консоль или продолжить работу. 
*   **Старт:** Команда `drn start` запускает невидимый дочерний `subprocess` с флагом `start_new_session=True` и мгновенно возвращает управление консолью пользователю.
*   **Управление PID:** Фоновый процесс узнает свой Process ID и записывает его в скрытый файл `~/.drn_agent/agent.pid`.
*   **Остановка:** Команда `drn stop` считывает номер PID из файла и шлет сигнал ОС `SIGTERM` для мягкого завершения всех потоков агента.

## 5. Сброс (Reset)
Если машину нужно вывести из сети или передать в другой проект, используется команда `drn reset`.
*   Она запрашивает подтверждение у пользователя `(y/N)`.
*   Останавливает фоновый процесс демона (если он запущен).
*   Физически удаляет папку `~/.drn_agent` со всеми ключами шифрования и белым списком.
